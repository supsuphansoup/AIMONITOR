## 2. 결함 상세 (모두 재현 확인)

### 2.1 시계열이 최신 구간을 조용히 버림 — **치명적**

`MAX_AGGREGATION_ROWS` 상한을 걸면서 `ORDER BY timestamp ASC ... LIMIT n` 을 썼습니다. 상한에 걸리면 **가장 오래된 n건이 남고 최신 데이터가 잘립니다.**

```
200건(오래된 100 + 최신 100), 상한 100 기준
수정 전: 버킷 1개, 최신 100건이 차트에서 사라짐 (경고 없음)
수정 후: 최신 구간 유지, 잘린 쪽은 partial=true 로 표시
```

모니터링 대시보드가 "지금"을 못 보여주는 것은 도구로서 실격입니다. 정렬을 `DESC` 로 뒤집어 **잘리는 쪽이 항상 과거**가 되게 했고, 잘린 경우 가장 오래된 버킷에 `partial: true` 를 실어 프론트엔드가 "구간 일부 누락" 을 표시합니다.

### 2.2 백분위수가 오래된 표본에서 계산됨

같은 원인. `latency_ms` 조회에 `ORDER BY` 자체가 없어 저장 순서(사실상 오래된 순)로 상한이 적용됐습니다.

```
최근 100건 = 10ms, 20시간 전 100건 = 5000ms, 상한 100
수정 전: p95 = 5000ms  (20시간 전 값을 "현재 P95" 로 보고)
수정 후: p95 = 10ms
```

건수·합계·평균은 SQL 집계라 원래부터 정확했고, 영향은 백분위수에 한정됩니다.

### 2.3 수동 평가가 다른 규칙의 쿨다운을 파괴

`POST /alerts/evaluate?ignore_cooldown=true` 가 **활성 규칙 전체의 `last_triggered_at` 을 `NULL` 로 덮어쓴 뒤** 평가했습니다. 대시보드의 "Evaluate Now" 버튼이 이 경로를 씁니다.

재현: 규칙 A가 1분 전 발동(쿨다운 60분) → 사용자가 규칙 B를 테스트하려고 버튼 클릭 → A의 조건이 이미 해소되어 재발동하지 않음 → **A의 쿨다운 기록이 영구 소실** → 2분 뒤 장애 재발 시 즉시 재알림.

쿨다운 무시를 **상태를 건드리지 않는 평가 옵션**으로 바꿨습니다. 수동 평가는 이제 이력 기록과 Webhook 발송은 하되, 쿨다운은 소비하지도 초기화하지도 않습니다.

### 2.4 다중 워커에서 알림 중복 발송

`evaluate_rules` 는 쿨다운을 **파이썬에서 읽고**, Webhook 을 보낸 **뒤에** `last_triggered_at` 을 씁니다. 그 사이 간격이 Webhook 왕복 시간(최대 5초)만큼 벌어집니다. `uvicorn --workers 4` 처럼 프로세스가 여러 개면 전부 "쿨다운 아님" 을 읽고 각자 알림을 보냅니다.

```
평가자 4개 동시 실행 + 400ms Webhook, 쿨다운 60분
수정 전: 알림 4건   ← 재현됨
수정 후: 알림 1건
```

`AlertEvaluator.claim_rule()` 을 도입해 **조건부 UPDATE(compare-and-set)** 로 발동 권한을 선점하게 했습니다.

```sql
UPDATE alert_rules SET last_triggered_at = :now
WHERE id = :id AND (last_triggered_at IS NULL OR last_triggered_at <= :cutoff)
```

`rowcount == 1` 인 호출자만 Webhook 을 보냅니다. 조건 평가는 선점 **이전**에 하므로, 조건이 맞지 않는 규칙의 쿨다운이 소모되지 않습니다.

### 2.5 오류 응답에 CORS 헤더 누락

요청 로깅 미들웨어가 500 응답을 **직접 만들어 반환**하는데, 그 미들웨어가 `CORSMiddleware` **바깥**에 있어 헤더가 붙지 않았습니다. 정상 응답과 preflight 는 정상이었고, 실패 응답만 해당됩니다.

브라우저는 CORS 헤더 없는 응답의 본문을 읽지 못하므로, 별도 도메인에 대시보드를 띄운 경우 500 오류가 **원인 불명의 네트워크 실패**로 보입니다. 등록 순서를 뒤집어 CORS 가 최외곽 계층이 되게 했습니다.

### 2.6 업그레이드 시 인덱스 미생성

`ALTER TABLE ADD COLUMN` 은 인덱스를 함께 만들지 못합니다. v0.2.0의 `ensure_schema` 는 컬럼만 추가했으므로, 업그레이드된 DB에서 `cost_source` 는 인덱스 없이 존재했고 이를 필터하는 집계는 풀스캔이었습니다.

인덱스 생성을 추가했습니다. 부수 효과로, v0.1.0이 `timestamp` 외에 만들지 않았던 `provider` / `model_name` / `status` / `trace_id` / `session_id` 인덱스도 함께 채워집니다.

### 2.7 `ensure_schema` 가 import 순서에 의존

테이블은 모델 모듈 import 의 부수 효과로 `SQLModel.metadata` 에 등록됩니다. 세션 모듈만 import 한 스크립트가 `init_db()` 를 호출하면 **빈 메타데이터를 대상으로 조용히 아무 일도 하지 않았습니다.** 앱 경로에서는 라우터가 모델을 import 하므로 드러나지 않던 잠재 결함입니다. `_load_model_metadata()` 로 명시화했습니다.

### 2.8 프론트엔드 자체 결함 (테스트가 발견)

`X-Total-Count` 헤더 폴백을 `Number(header)` 로 판정했는데 `Number(null) === 0` 입니다. 헤더를 노출하지 않는 배포에서 **행이 있는데도 "표시할 트레이스 없음"** 이 나옵니다. 이번에 새로 작성한 프론트엔드 테스트가 잡아냈습니다.

## 3. 추가 기능

### 3.1 요청 본문 크기 제한

`MAX_BATCH_SIZE` 는 JSON 파싱이 끝난 뒤에야 적용되므로, 거대한 단일 페이로드가 메모리에 통째로 올라오는 것을 막지 못합니다. `Content-Length` 를 읽어 본문을 읽기 전에 413 으로 거절합니다 (`MAX_REQUEST_BYTES`, 기본 8MiB).

요청 속도 제한(rate limit)은 이번에도 넣지 않았습니다. 모니터링 데이터를 조용히 버리는 부작용이 크고, 리버스 프록시 계층이 더 적합한 위치라고 판단했습니다.

### 3.2 진짜 페이지네이션

`GET /traces` 가 `X-Total-Count` 헤더로 전체 건수를 반환합니다. 기존에는 "페이지가 꽉 찼으면 더 있겠지" 로 추측했습니다. 정렬에 `id` 를 2차 키로 추가해, 타임스탬프가 같은 행이 두 페이지에 걸쳐 중복 표시되는 문제도 없앴습니다.

대시보드는 `1–50 / 158건 · 1/4 페이지` 형태로 표시합니다.

### 3.3 CSV 내보내기

`GET /api/v1/traces/export.csv` — 비용 정산과 스프레드시트 분석용. 두 가지 설계 결정이 있습니다.

- **`error_message` 와 `metadata_json` 은 내보내지 않습니다.** 내보내기는 트레이스 내용이 시스템 밖 파일로 빠져나가는 가장 쉬운 경로이고, 비용 정산에 이 두 컬럼은 필요 없습니다.
- **단가 미상 호출의 비용은 `0` 이 아니라 빈 칸입니다.** 스프레드시트에서 합계를 낼 때 "모름" 이 "공짜" 로 둔갑하지 않습니다.

응답은 스트리밍이라 대량 내보내기에서도 서버 메모리에 전체 파일이 올라가지 않습니다.

### 3.4 알림 집계 재사용

같은 시간 창을 쓰는 규칙들이 집계를 공유합니다. 규칙 13개(창 2종) 기준 집계 호출이 13회 → 2회로 줄었습니다.

### 3.5 프론트엔드 테스트 (v0.2.0의 미완 과제)

Vitest + Testing Library 로 **53개** 테스트를 추가했습니다.

`DATABASE_URL` 은 SQLAlchemy 가 지원하는 모든 DB를 받지만 검증은 SQLite 로만 해왔습니다. 집계·CAS UPDATE·삭제·DDL 을 **PostgreSQL / MySQL dialect 로 컴파일**해 SQLite 전용 문법이 섞이지 않았는지 확인합니다. 서버 없이 도는 가드레일이며, Postgres 실제 구동 검증을 대체하지는 않습니다.

## 5. 업그레이드

```bash
git pull
pip install -r backend/requirements.txt
docker compose up --build -d
```

v0.2.0 → v0.3.0 은 **스키마 변경이 없습니다.** 다만 시작 시 누락 인덱스가 자동 생성되므로, 큰 테이블에서는 첫 기동이 평소보다 몇 초 길어질 수 있습니다.

동작 변경 한 가지: **"Evaluate Now" 가 더 이상 쿨다운을 초기화하지 않습니다.** 이 부작용에 의존해 알림을 강제 재발송하던 운용이 있었다면, 해당 규칙의 `cooldown_minutes` 를 조정하세요.
